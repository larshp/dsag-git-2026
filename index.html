Why Git in ABAP?

Why?
Oh why?

Code is only one part of a safe change.

Reason 01

Shift left

A problem is cheapest the moment it is created. Git moves every check that can run early to the point where the change is still being written.

  1. Write
  2. Commit
  3. Pull request
  4. Review
  5. Release

Checks run here

Same checks, sooner

Static analysis, unit tests and project rules do not change. What changes is when they run — while the author is still working on the change.

How it works · 01

One system, many branches

Git assumes every developer has their own working copy. ABAP development happens in one shared system, where every object exists exactly once — and a change can start in Git or in the development system.

Developer Afeature/invoice-splitDEVK900123
Developer Bfeature/order-batchDEVK900456
Developer Cfix/posting-dateDEVK900789
either direction
DEV One development system

Three developers at once, no local checkout, no second copy. One active version of every object, separated only by transports.

Which change belongs to which branch?

Nothing in the system answers that. Two developers can touch the same object in the same week, and the branch, the pull request and the review all live somewhere else.

How it works · 02

abapGit Flow

Every transport next to its branch, its pull request and the checks that ran — without leaving the development system.

How it works · 03

Editing off stack

Once the code is files in a repository, the edit, check and run loop no longer needs the shared system — no logon, no object lock, no transport.

01

Edit

Clone the repository and work in your own editor. abaplint’s language server gives syntax, navigation and quick fixes on plain files.

02

Check

abaplint applies the rules the project agreed on — naming, obsolete statements, the target release — in milliseconds, without a system.

03

Run

The abaplint transpiler turns the ABAP into JavaScript and open-abap supplies the runtime, so ABAP Unit runs on Node.

The same rules run in CI

What passes on a laptop is what the pull request checks again. The system is left for what genuinely needs it: real data, real integration, the final test.

Git and the agents

Where this comes from

Two groups have looked at what actually makes AI pay off on a codebase. Neither of them is talking about ABAP — and both land on the repository.

DORA

dora.dev/ai

Google’s research programme on software delivery. The 2025 report on AI-assisted development, and the capability guides behind it — including the one on version control.

Factory

factory.com/agent-readiness

An evaluation framework that scores a repository on how ready it is for autonomous agents — documentation, tests, CI, modularity — and publishes the results for open-source projects.

Git and the agents · 01

Agents need files

A coding agent reads, diffs and patches files. ABAP objects live in the database, where it can do none of that.

Git and the agents · 02

The safety net

Generated code is only safe to try when it is trivial to inspect and to undo.

Strong version control practices are the essential safety net that allows teams to experiment with AI-generated code confidently.DORA · Version control

dora.dev/ai

Git and the agents · 03

Something has to check

An agent writes code far faster than a person can read it. Continuous integration is what keeps up.

01

It builds

Syntax and project rules checked on every push. abaplint does this without an SAP system.

02

It is tested

ABAP Unit says whether the behaviour still holds, not only whether it compiles.

03

You hear back

The verdict lands on the pull request in minutes.

More change needs more checking

DORA found the same: without automated testing, mature version control and fast feedback, more change means more instability.

dora.dev/ai

Git and the agents · 04

Iterate off stack

An agent’s first ten attempts should not land anywhere near a real system.

No system in the loop

abaplint parses and checks a plain checkout — no SAP instance, no logon.

Code that runs

open-abap executes ABAP and its unit tests on Node, so an agent can try what it just wrote.

Nothing to damage

Seconds per attempt, against a checkout rather than your development system.

Git and the agents · 05

The repository is the context

Everything an agent needs to make a change sits in one checkout, versioned together.

ABAP source Unit tests Documentation CI configuration Prompts Agent instructions
Better codebases, better outcomes

Factory scores repositories on documentation, tests, CI and modularity. The same things that already made a codebase good to work in.

factory.com/agent-readiness

Git and the agents · 06

A person still decides

Everything so far makes a change cheap to produce and cheap to check. None of it decides whether to keep it.

The pull request is still the gate

A change waits there until somebody merges it. Agents change how fast the queue fills up. They do not change who signs off on it.
